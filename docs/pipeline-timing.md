# Local multi-cycle pipeline timing

The pipeline runner measures authenticated local preprocessing, a verified feature-cache round trip, fixed unit mapping/tensorization, CPU/MPS batch transfer, bounded engineering train and validation passes, and checkpoint write/reload. Timing receipts are engineering evidence. They contain no forecast scores or predictions, and do not establish a study split, epoch choice, convergence, or cloud budget.

`scripts/benchmark_pipeline.py` prints a plan by default. Supply a private builder-request JSON using the `build_multicycle_development` arguments, an explicit chronological validation origin, candidate architecture/device, and the history length. Execution requires `--execute`, a new directory under ignored `runs/` or `.local/`, a positive `--max-updates`, and the exact plan digest with `--approved-plan-sha256`. The digest binds request bytes, implementation hashes, fixed unit mapping and all timing settings. Failed attempts retain their precharge; reusing a run directory is refused. This tool does not automatically retry or increase an allowance.

For the retained five-cycle development cohort, L168, batch eight, gauge `03161000`, validation origin `2024-02-29T02:00:00Z`, and three engineering epochs imply six optimizer updates per candidate. An eight-case CPU/MPS × four-architecture campaign therefore needs 48 explicitly allocated updates. This is a proposed run geometry, not a claim that the campaign ran; inspect its current report.

The builder performs one first pass in a fresh worker process and one warm pass in that same worker. Both authenticate sources. Their arrays and provenance must match exactly. The OS disk cache is not flushed: “first pass” is not a claim of physically cold storage. The cache is compressed NPZ, contains only bounded arrays/coordinates, is written with `fsync`, and is checked by byte and array hashes on reload. Raw source data, private cache contents, checkpoint weights, and request paths stay out of Git.

Models use the existing fixed engineering unit mapping, not fitted scalers. Each model uses one explicitly selected gauge. The timing split retains validation origins at or after the chosen boundary; training origins must have their final target at or before that boundary. Boundary-crossing training windows are purged. All labels must precede the protected assessment period. Missing predictors retain masks and become zero placeholders only after the declared unit mapping. Targets never enter model forward arguments.

No warmup updates are hidden. Every engineering pass, including the first, is recorded. CPU uses an explicit copy and MPS uses synchronized device transfers. Update timing includes model/loss/gradient/parameter checks; validation timing includes masked-loss finite checks and prediction transfer to CPU. Epoch wall durations also include host looping and resource checks. Validation losses are discarded. Checkpoint write includes transfer to CPU and durable write; reload includes identity verification, model/optimizer reconstruction and state loading. Exact eval-mode forward replay is checked separately; this is not a resumed-optimizer parity test.

Each completed receipt records Python and dependency versions, operating system/release and machine architecture, Torch intra-op/inter-op thread counts, FP32 precision, width64 and MPS availability. Hostnames and local filesystem paths are excluded.

The supervisor enforces the configured wall limit (at most 900 seconds) and observed combined parent/worker RSS plus MPS-driver memory (at most four GiB). The child also checks limits between stages. MPS driver memory is sampled; these are process-level engineering guards, not container isolation. Worker network access is denied, model loading is offline, and unavailable MPS fails without a CPU substitute. The local `RunJournal` retains terminal state, update allowance, artifact hashes and Prometheus metrics.

`estimate_workflow` projects a caller-specified number of training/validation cases, epochs, trials, seeds and gauges using the observed batch geometry. Its estimate includes measured startup/cache-read/tensorization, updates, validation cadence and checkpoint cadence. Every incomplete final batch is charged as a measured batch. It does not assume that a larger batch has the same per-case speed. Source preprocessing is reported separately because a small resident cohort cannot determine full-corpus or cloud-read scaling. Convergence, scheduler/recovery overhead and cloud throughput remain unmeasured. An optional hourly rate is caller-supplied arithmetic only; it is neither a current provider price nor authorization to spend.
